最終更新: 2026-09-29

## 0. 前提

- **締切**: なし。この作品＋面接で内定が決まるまで継続制作。
- **優先方針**: 基盤(遊べる土台)が無ければ演出・技術アピールも成立しないため、**基盤・土台系のタスクを優先**しつつ、並行できるものは並行する。
- **参考タイトル**: スターフォックス(リメイク), パンツァードラグーン リメイク, パンツァードラグーン オルタ, Rez HD ※これらが仕様を縛るものではなく、あくまで参考。
- **稼働見込み**: 週20時間以上。
- **ボリューム感**: **1ステージを密度高く作る**(2026-09-29決定)。ステージ追加はデータ追加で済む状態を保つ。
- **スコープ外**: タイトル画面と関連演出は別課題として進めるため、このロードマップでは扱わない。
- **直近の稼働**: 1日4〜7時間(タイトル演出と並行のため)。
- **10/19(月)に進捗発表あり**: 基盤を早く固め、技術発表用の要素を作る時間を確保する。発表の技術ネタ選定は別セクションで進める。
- **評価観点の参考資料**: `photo/` に先輩の自作エンジン就活作品へのフィードバック例あり。○/×を分けている典型パターンを [§4](#4-コード品質チェックリスト先輩フィードバックより) に抽出済み。**機能の有無だけでなく実装の質(未実装コードを残さない・クラス肥大化・命名統一等)も同格の評価対象**という前提でタスク化する。

## 2.5 今週の基盤スプリント(〜10/2 金)

**詳細な実行指示書は [FOUNDATION_SPRINT.md](FOUNDATION_SPRINT.md)**(現状診断・タスクごとの仕様・完了条件・進め方のルール)。以下は要約。

**方針**: 演出・作り込みの前に、遊びの土台(照準→発射→ロック→相殺→HP/スコア表示)を確立する。回避演出(D)は後回し。

**決定事項**
- ホーミング弾は**ロック対象がいる時だけ**発射する。通常弾は対象指定なしで**レティクル方向**へ飛ぶ。
- ホーミングの見た目は**弾頭が飛び、軌跡をリボン状ビームで描く**方式(パンツァードラグーン風)。ベジエ誘導は維持。
- 敵弾の相殺は**機能として持たせるだけ**。どの弾を撃ち落とせるかはレベルデザインで決める。
- 入力は**マウス+パッド両対応**。既存のキー割り当て(Space/パッドA/マウス左など)は維持し、アクション単位に集約する。

**タスク(実行順・見積もりは目安)**

| 順 | タスク | 内容 | 見積もり |
|---|---|---|---|
| 1 | F-min+入力抽象化 | 入力/弾生成/HUD描画をGameSceneから切り出す(1191行)。入力は「照準/撃つ/ロック/回避」のアクション単位に集約 | 6〜8h |
| 2 | A / A' + ロック管理 | 通常弾をレティクル方向へ、ホーミングは対象がいる時のみ。撃破/画面外時の参照切れ対策 | 6〜9h |
| 3 | C-fn | 陣営(自/敵)と弾種別の統一、撃ち落とし可否の属性、自弾と敵弾の衝突・破壊 | 3〜4h |
| 4 | E-min | 体力・スコアのスプライトUI(ImGui依存から卒業)。ロック数表示は余裕があれば | 4〜5h |
| 5 | B | リボンビーム。まず動く最小版 | 8〜10h |
| 6 | Release確認 | ImGuiなしで通しプレイできるかの点検 | 1h |

**切り分け**: 1〜4が金曜までのコア。B(最小版)とRelease確認は間に合わなければ翌週前半へ。

**目安スケジュール**
```
火 F-min+入力抽象化に着手 / 水 F-min完了→A・A'・ロック管理
木 C-fn→E-min           / 金 B(最小版)、余裕があればRelease確認
10/3〜10/8   回避演出(D)、サウンド最小組み込み、ボス弱点
10/9〜10/14  発表用の技術トピックの実装・検証
10/15〜10/18 スライド作成・リハーサル(7〜8分)
10/19        発表
```

**発表ルール(スライドより)**: 要素別コンテストの内容は禁止。自分で見つけた課題が望ましい。タイトルは内容が分かる名前にする(「進捗報告」は不可)。7〜8分で、なぜそれを作ったか・どこに工夫したかを語る。

## 4. コード品質チェックリスト(先輩フィードバックより)

`photo/`のフィードバック例から、○評価と✕評価を分けていた典型パターンを抽出。M4で総点検する際のベースにする。

**✕評価でよく指摘されていたパターン**(この卒業制作でも要注意):
- 機能が「宣言のみで未実装」のまま残っている(例: 他作品のボスBehaviorTreeが空 → **この作品の`BossComponent::Update`と同じ状況**、最優先で潰す)
- クラスの肥大化(GameScene 750行超、BossEnemy 2000行超などの実例あり)
- 生ポインタの多用・ダングリングリスク(delete後の参照、shared/weak不使用)
- AIの攻撃パターン選択を文字列比較で行っている(enum/関数テーブル化が望ましい)
- 命名規則の不統一、マジックナンバーの残存
- null チェックの一貫性の欠如(チェックする箇所としない箇所が混在)
- 重複コードが多く、クラス分けが機能していない
- コメントアウト放置・未使用コードの残存

**○評価で評価されていたパターン**(自作エンジンとして伸ばすべき方向):
- データ駆動のクラス設計、STLの活用
- ステートマシン/AI構造の明確な設計
- unique_ptr/weak_ptr等の堅実なメモリ管理
- マジックナンバー回避、命名規則の統一
- 自作DX12エンジンとしての描画/パーティクル/ポストエフェクト/シーン状態管理の作り込み(この作品はまさにこの路線で強みがある)
