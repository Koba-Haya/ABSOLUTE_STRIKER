## 0. スレッドの運用ルール(最初に読む)

- **親スレッド = 相談・設計の決定。子スレッド = 実装。** 親で決めた内容を子が実装し、子で相談事(設計の分かれ道、仕様の疑問)が出たら親へ回す。
- 互いの情報はこのファイルで共有する。
  - 決定事項(2 章、3 章)は親が更新する。
  - 実装の状況(9 章の進捗ログ、判明した事実、困りごと)は子が更新する。
  - 子は作業の区切りごとに 9 章へ追記する。親へ回す相談事は 10 章に書く。
- **git の書き込み(commit / push / branch / merge)はしない。** ユーザーが差分を見てから行う。変更が済んだら要約を伝えるだけで止める。
- 1 回の作業は 1 つの目的に絞る。途中で別の問題を見つけても、勝手に直さず報告だけする。各ステップの後に、ビルドと動作確認を済ませてから次へ進む。
- 実装したら「何をしたか」だけでなく「なぜそうしたか」「どの概念に基づくか」も書く。ユーザーは自分で理解して進めることを重視する(コードを書いたあとに詳しい解説をする)。
- 日本語で説明する。コメントは細かく日本語で書く。コメントや文字列に絵文字・装飾記号は使わない。マジックナンバーは名前付き定数にする。
- 新しい .cpp / .h を足すときは `Application.vcxproj(.filters)` / `AbsoluteEngine.vcxproj(.filters)` へ追加する。
- Claude は実機の画面を直接見られない。見た目の最終判断はユーザーの目。確認用に Blender で画像を描画して見るのは可。
- ビルド、シェーダーの落とし穴は [TRANSITION_HANDOFF.md](TRANSITION_HANDOFF.md) の 8 章を参照。

## 2. 決定事項(ユーザーと合意済み)

- 自機を**蝶**にする。モデルは Claude が Blender で生成する。**ボーン付き**で、アニメーションもさせる。
- 崩壊の表現は **ディゾルブ(ノイズで朽ちる)+ シャード(ポリゴン破片)+ 鱗粉(パーティクル)の重ね掛け**。
- 演出は雲ステージだけ(今は複数ステージがない)。**雲を先に作り、海は後から同じ流れで足す**。雲も海も、最終的には本格的にやる(水・雲・粉々の表現はシェーダー等で積極的に使う)。
- カメラワークを駆使して魅せる。死亡カメラはレールとは独立した状態にする(演出担当クラスを作る。[GameIntroDirector](../Application/scene/GameIntroDirector.h) と同じ作り方)。
- 演出の長さは全体で **4〜6 秒を上限**。決定ボタンで**スキップ**できる。
- アニメーションは**案 2**: 1 ファイルに複数のアニメーションを入れ、**名前で選べる**ようにローダーを拡張する。
- 展示モードは **ゲームから始めてゲームへ戻る**ループ(タイトルは通らない)。クリアは見せなくてよい。5 章を参照。
- 翅の色は **mix**(前翅は青から紫の玉虫色、後翅は青緑と橙・桃の斑点)に決定(2026-10-24)。玉虫色の「角度で色が変わる」輝きをシェーダーで足すかは、1c のあとで相談する。
- **自機を竜から蝶へ差し替える**(2026-10-24 決定)。差し替えはステップ 1c で行う。蝶は竜より小さい(翼幅約 2.7)ので、カメラとの距離と当たり判定の大きさを決める。
- 未決: スタート演出(竜の上を弧で飛び越える演出。[STAGE_START_HANDOFF.md](STAGE_START_HANDOFF.md))への影響。自機が蝶になると、竜を前提にした部分(スケール、軌道)の調整が要る。1c で影響範囲を調べて親へ報告する。
- **1c の決定(2026-10-24)**:
  - 自機の蝶は、**翼幅 3.7(`FitToWingspan(3.7)` のまま)、当たり判定は半径 1.0 のまま**にする。
  - **向きはモデル側で直す。エンジン(`MakeLeftHanded`)は触らない。** `MakeLeftHanded` は座標系の変換(右手系 -> 左手系)で、形式ごとに外すとモデルが左右反転し、アニメも鏡像になる。glTF の書き出しは前方の軸を選べず、Blender の -Y 正面が頭 +Z になり、エンジンで反転して後ろ向きになる。そのため、蝶は Blender で +Y 正面(頭が +Y 側)に作り直す。
  - **発射位置は、頭の先に `muzzle` ボーンを足す**(頭の子。アニメに追従して違和感を減らすため)。ウェイトを持たないボーンが Assimp 経由でエンジンのスケルトンに残るかは、要確認。仮の赤い立方体の武器は消す(人型モデルの頃の名残で、蝶には不要)。
  - 弾、リボンの尾、ロックオンのミサイルの発射位置は、`muzzle` ボーンのワールド位置にする。
  - 進め方は段階的: 1c-1(向きと `muzzle`、アニメの窓口と再生終了の判定、自機の差し替えと表示確認)、1c-2(接触距離、アニメの切り替え)、1d(タイトルシーン)。**1d は、死亡演出の核(4 章のステップ 2〜8)の後に回す**(展示ループはゲームから始まるため)。時間があれば入れる。
- **蝶の見た目の傾き(2026-10-24 決定)**: 実機で、真後ろのカメラから見ると翼が細い線に見えた(羽ばたきは翼の面が体の軸を含む面の中で動くため、真後ろからは常に真横を向く。実際の蝶は体を斜め上に向けて飛ぶので広く見える)。**モデルに機首上げ 30 度を焼き込んで再生成する**(ユーザーの決定。エンジン側の定数にはしない)。角度は生成スクリプトの定数にして、あとから変えられるようにする。
- **被弾・撃破まわりの演出の整理(2026-10-25 決定。ステップ 2 の前に実施)**: ポストプロセスは、授業で習った直後にとりあえず当てはめたものが多く、余計で見づらい。次を削除する: ロックオン中のアウトライン、瀕死のグレースケール、現在の GPU パーティクルのバースト(爆発パーティクルは、のちに GPU へ移す。CPU の爆発パーティクルはそれまで残す)、カメラシェイク(計算だけで未適用)、敵出現のぼかし(未呼び出し)、旧型スケールエフェクト、撃破時の画面の歪み、キルストリークのノイズ、調査用の一時ログ。爆発ライトは弱める。残す: 被弾の Vignette、加速のブラー、撃破の CPU パーティクルとリング、敵のディゾルブ。ボス関連は保留。瀕死は「画面の周りの枠だけ赤くする」案も出ている(ユーザーの判断待ち)。
- **演出整理の結果(2026-10-25 確認済み)**: 整理後の見た目は、ユーザーが実機で確認して OK。撃破の手応えは減ったが、いまは演出の見やすさが優先。**撃破の手応えは、ゲームシステムを作り込むときに、適したものを追加する**(今は触らない)。瀕死は、グレースケールの代わりに「画面の周りの枠だけ赤くする」ことに決定(HP が `kCriticalHp` 以下のあいだ。静かに脈打たせる程度)。
- **霧の役目**: 霧は「覆い(シーン入れ替えを隠す)」「雲の中の表現」「水滴の舞台」の役目を持つ。霧(`fog`)と水滴(`wetness`)は別のパラメータで、水滴だけでも出せるが、そのときは画面を覆う別の仕組みが要る。代案: 雲そのものに沈んで覆う(CloudDive の雲を下向きに使う。ゲーム内の雲海と合うかは未確認)。いまは、深度の霧 + 水滴の案で進める。
- **ステップ 2 の設計を承認(2026-10-25)**: 死亡演出クラス `PlayerDeathDirector` + `GamePhase::Dying` + 世界の時間スケール(ヒットストップの後にスロー)+ スキップは Enter / パッド Start + `Dying` 中は自機を無敵。**スキップの「受け付けない猶予」は 0 にする**(`kSkipGuardSeconds = 0.0f` として、変えられる形で残す)。展示モード中はスキップ無効。
- **スキップキーの訂正(2026-10-25)**: ユーザーの意図は「スキップのキーボード操作を `0` のキーに割り当てる」(受け付けない猶予を 0 にするのではない)。キーボードのスキップキーは `DIK_0`(Enter は、デバッグのショートカット(Enter = クリア)と衝突していた)、パッドは Start のまま。猶予 `kSkipGuardSeconds` は元の 0.5 秒に戻す。
- **ステップ 2 と霧の確認(2026-10-25)**: ステップ 2(`Dying` の土台)は、ユーザーが実機で確認して OK。死亡カメラは、ステップ 4 なので、まだ(いまは、レールが止まった姿勢のまま)。霧の作り直し(深度の霧)も、録画で確認して OK(深度は正しく読める。覆いは空と雲海から先、竜が最後。晴れは竜が先)。残る課題: 霧の濃淡と太陽側の明るさが控えめ、雲海と空に距離がない(雲海は水平面との交点で距離を求める案)、覆いの時間の曲線(段階 F)。次は、ステップ 3(崩壊)の設計相談と、水滴の段階 B(小粒)。
- **霧の作り直しを承認(2026-10-25)**: 深度に応じた霧(視程を遠くから近くへ縮める、晴れるときは近くから)、太陽側の明るさ、縞のノイズの濃淡、最後の覆い。最初に、深度の読み取りをデバッグ表示で確認する。

## 3. 全体の流れ(演出)

```
被弾で HP 0
 -> ヒットストップ(一瞬止まる)
 -> 蝶がボロボロに崩れる(翅が朽ち、裂け、鱗粉と破片が散る)
 -> 破片が落下。死亡カメラが追う
 -> 雲海へ着地(雲のもわっと)
 -> 霧と水滴で覆う(ステージ別の遷移)
 -> GameOverScene(バナー)
```

## 5. 展示モードの方針

## 6. 水滴の目標(エースコンバット 8 の動画の分析)

| 区間 | 見えているもの | 実装での言い換え |
|---|---|---|
| 霧の中 | 画面全体が灰青色の単色に近づき、コントラストが落ちる。機体も霞む | フォグ濃度を上げ、彩度とコントラストを下げる |
| 抜ける瞬間 | 水滴が一気に付く。大粒は縁が明るく、背景が歪んで見える(屈折)。小粒は暗い点で密 | レンズ水滴のシェーダー |
| 抜けた後 | 水滴は外周へ流れて消える。大粒は残りやすい。太陽のグレア、フレア、虹色のゴースト | 水滴の寿命と流れ、ブルーム、フレア |

- 完成度の正体は、水滴の「付く -> 流れる -> 消える」という**時間の流れ**。静止した模様として置くと「形だけ」になる。
- 手法: セルごとに乱数で水滴の位置・大きさ・寿命を決め、法線から屈折方向を求めてシーンを少しずらして読む。流れの跡は縦長のセルで描く(Heartfelt 式)。`wetness`(濡れ具合)のパラメータで時間制御し、流れる向きは前進の風に合わせて外周へ向ける。
- タイトル -> ゲームの雲抜け(既存の `CloudDive`)でも使い回す。既存の遷移の基盤は [TRANSITION_HANDOFF.md](TRANSITION_HANDOFF.md) の 2.1 章を参照。
